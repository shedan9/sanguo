# 三国行纪 基础战斗开发规则

日期：2026-11-12。状态：已实现的通用单位开发子集；规则包`rules.basic-development.v1`，尚未完成OL来源冻结与M1验收。

## 1 实现入口与范围

`src/Sanguo.BattleCore/Basic/`提供纯函数规则执行、不可变状态、合法动作及控制者视图。应用层`BasicBattleSession`是单写入命令入口；基础设施`BasicBattleSnapshotCodec`负责独立开发快照。它们与G0抽牌会话分开版本化，原G0内容摘要、存档与种子42终态哈希保持不变。

当前角色均为无武将技能的通用单位，每方1至4人，两方人数可不同。配置顺序决定唯一座次和先手，双方队伍ID由配置提供。一个控制者可操作多名单位，每条命令仍须同时匹配当前控制者和操作实体。

仅支持实体杀、闪、桃。正式OL人物、装备、判定、锦囊、原创技能、双将、车轮、任务、城池和奖励均未接入；Godot客户端仍为G0抽牌探针。本批来源清单继续保持待核验，开发规则及合成牌组不进入正式OL内容目录。

## 2 当前采用的明确语义

| 环节 | 开发规则行为 |
| --- | --- |
| 开局 | 全牌组PCG32洗牌；每人默认4张初始手牌，再由先手摸2张；测试夹具可指定初始手牌数为0 |
| 回合 | 无相关能力时直接进入摸2张、出牌、按当前体力弃牌；弃牌逐张选择，完成后进入下一个存活单位 |
| 杀 | 出牌阶段限一次；选另一名存活角色，可以选同队；活座次环的最短距离不超过1，无装备修正 |
| 闪 | 只在杀的目标响应请求中支付一张；可放弃；成功响应不造成伤害 |
| 桃 | 自己出牌时仅可回复自己1点，满体力拒绝；濒死救援时可回复当前濒死者，包括自己或敌方 |
| 伤害 | 本批普通杀造成1点伤害，记录来源、目标、实体牌与数值；体力降至0或以下挂起救援 |
| 救援顺序 | 从当前回合单位开始，沿存活座次环依次询问，包含濒死者；每位救援者可连续用桃或放弃；回复到正体力才结束救援 |
| 救援失败 | 所有存活单位放弃后，濒死者死亡、手牌进弃牌堆；没有身份奖惩；死亡位置退出距离图与后续回合 |
| 牌堆不足 | 仅将弃牌堆重新洗入摸牌堆；处理区始终排除；仍不足时记录`draw.exhausted`并停止本次剩余摸牌，不产生胜利 |
| 终局 | 当前效果栈清空后，一方无存活单位则另一方胜；无车轮替补、战役胜利ID或占城事件 |

上表是当前可执行的开发合同。开局发牌顺序、先手摸牌、距离、救援顺序、洗牌及无牌处理仍须对照同一OL PC快照核验；如有差异须改实现或登记项目裁定，不能将本表当作冻结的OL裁定。负体力连续救援已有注入稳定状态的回归，但本批普通杀只造成1点伤害，不宣称多点伤害或技能已接入。

## 3 结算与决策契约

使用杀时实体牌进入处理区，压入`FinishCard`帧和`Dodge`帧。目标放弃闪后，以显式`Damage`帧结算伤害；需要时压入`Rescue`帧并记录救援游标。伤害不需要选择时自动推进，稳定暂停点只保留等待闪或桃救援的帧及其收尾帧。救援和死亡清理完成后才执行`FinishCard`，将原杀放入弃牌堆，再判断终局。闪与桃自身的支付立即完成，原杀在其响应全程留在处理区。

每个稳定状态携带唯一实体牌清单，实际摸牌堆、各单位手牌、处理区和弃牌堆的并集必须恰好等于清单，不能重复、缺失或增加实例。快照还校验体力/存活状态、双方容量、连续座次、帧来源与目标、支付牌、游标、待决策请求及命令记录。日志按连续序号记录抽牌、杀、响应、伤害、回复、濒死、死亡和终局。

命令包含`CommandId`、预期版本、控制者、请求ID、操作单位及动作。应用层先检查重复ID，再检查版本和权限，最后以规则核心提供的合法动作检验时机、支付、目标、范围和次数。完全相同的重复命令返回原提交结果；同ID不同输入拒绝。被拒绝的命令不提交状态、不消耗随机流、不增加日志或扣牌。救援中连续用桃也会更新版本和请求ID。

`BattleView`公开体力、队伍、座次、手牌数、处理区和弃牌堆；只给控制者自己的手牌。摸牌堆只给数量，不提供顺序和随机状态；只有当前控制者能取得合法动作及其支付牌。完整`BattleState`及内部事件日志只供规则、存档和开发工具使用，不能直接绑定客户端或AI。当前演示脚本只读取操作控制者的视图，它是固定操作脚本，尚未实现正式战术AI。

## 4 开发快照及复现

基础战斗快照使用格式ID`sanguo.basic-battle`、格式版本1，记录引擎`0.2.0-basic-development`、规则包、场景内容摘要、随机流、全部区域、效果帧、请求、日志和去重记录。信封采用SHA-256检测损坏，恢复时检查版本、预期内容摘要和领域语义；不兼容快照直接拒绝。

本批只实现编解码。命令行输出的是开发证据文件，尚未接入G0的原子替换、备份回退文件服务或Godot保存按钮；不应将其作为玩家存档服务的已完成验收。

```sh
# 全量回归，含独立进程恢复后final.json逐字节比对
./scripts/check.sh

# 合成64张牌、通用单位2对2、种子42
./scripts/dotnet.sh run --project tools/Sanguo.Simulator -- --battle-basic 42 build/basic-battle

# 新进程读取最后一个稳定决策点并继续
./scripts/dotnet.sh run --project tools/Sanguo.Simulator -- --battle-resume build/basic-battle/checkpoint.json build/basic-battle/resumed
cmp build/basic-battle/final.json build/basic-battle/resumed/final.json
```

输出`checkpoint.json`、`final.json`、内部`events.json`和`report.json`。逐决策执行“写文件→读文件→提交同一命令→比较哈希→重提命令确认幂等”。报告按出牌、弃牌、闪响应和救援记录恢复数量；超过4000步视为失败，不产生胜利。证据目录必须使用独立目录，脚本会覆盖同名开发证据文件。

种子42场景实际完成26个角色回合、105条命令；恢复点分别为出牌55、弃牌17、闪响应26、救援7。终态SHA-256：`feaee91bff0737c36d442de1c560cdfa17b51a84c5f9183fc4145f584e66d8b4`。独立进程从最后救援点恢复后，终态快照与连续执行逐字节一致。

## 5 验证范围与后续

新增33项xUnit检查，包含杀闪牌去向、伤害来源、桃使用资格、主动杀次数、距离、弃牌、负体力救援、自救、救援座次环绕、全员放弃后的死亡清理、死亡后距离和回合、空牌堆、洗牌随机恢复、非法命令不变、共享控制者的实体权限、并发/重载幂等、可见信息隔离及快照篡改和语义错误。

批量检查另外覆盖16种双方人数配置和100个固定种子的2对2合成杀牌对局，每个决策点都编码恢复、执行同一命令并比对完整哈希，持续检查实体牌守恒。这些样本不含锦囊或武将，不充作M1全部内容的100场验收。完整`check.sh`当前通过124项xUnit及13项Python检查，G0原终态哈希不变。

下一步接入锦囊的交替响应、无懈窗口及触发框架，再接入关羽、曹操与奋击；客户端消费控制者视图和合法动作。正式规则及UI还原仍需来源冻结和对应验收证据。
