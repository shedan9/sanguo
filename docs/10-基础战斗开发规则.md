# 三国行纪 基础战斗开发规则

日期：2026-11-12。状态：已实现的通用单位开发子集；规则包`rules.basic-development.v2`，尚未完成OL来源冻结与M1验收。

## 1 实现入口与范围

`src/Sanguo.BattleCore/Basic/`提供纯函数规则执行、不可变状态、合法动作及控制者视图。应用层`BasicBattleSession`是单写入命令入口；基础设施`BasicBattleSnapshotCodec`负责独立开发快照。它们与G0抽牌会话分开版本化，原G0内容摘要、存档与种子42终态哈希保持不变。

当前角色均为无武将技能的通用单位，每方1至4人，两方人数可不同。配置顺序决定唯一座次和先手，双方队伍ID由配置提供。一个控制者可操作多名单位，每条命令仍须同时匹配当前控制者和操作实体。

当前支持实体杀、闪、桃、决斗、无中生有、无懈可击，共六种牌。正式OL人物、装备、判定、拆顺等其他锦囊、原创技能、双将、车轮、任务、城池和奖励均未接入；Godot客户端仍为G0抽牌探针。本批来源清单继续保持待核验，开发规则及合成牌组不进入正式OL内容目录。

## 2 当前采用的明确语义

| 环节 | 开发规则行为 |
| --- | --- |
| 开局 | 全牌组PCG32洗牌；每人默认4张初始手牌，再由先手摸2张；测试夹具可指定初始手牌数为0 |
| 回合 | 无相关能力时直接进入摸2张、出牌、按当前体力弃牌；弃牌逐张选择，完成后进入下一个存活单位 |
| 杀 | 出牌阶段限一次；选另一名存活角色，可以选同队；活座次环的最短距离不超过1，无装备修正 |
| 闪 | 只在杀的目标响应请求中支付一张；可放弃；成功响应不造成伤害 |
| 桃 | 自己出牌时仅可回复自己1点，满体力拒绝；濒死救援时可回复当前濒死者，包括自己或敌方 |
| 决斗 | 出牌时选择另一名存活角色，不受攻击距离限制；先开放无懈窗口，生效后由目标开始交替响应一张杀，失败者受另一决斗者1点伤害；响应杀不消耗或重置主动杀次数，不再逐轮开放无懈 |
| 无中生有 | 出牌时仅指定自己；无懈窗口结束且效果生效后摸2张；无阶段次数限制 |
| 无懈可击 | 仅在锦囊无懈窗口中使用，绑定当前最新待反制实体；可反制上一张无懈，不能用于杀、决斗出杀或濒死请求 |
| 无懈询问 | 从当前回合单位沿存活座次环询问全员；每张无懈支付后重新从当前回合单位询问，原来放弃者可再次参与；全员放弃才关闭窗口 |
| 连续反制 | 奇数张无懈取消原效果，偶数张恢复原效果；链上各无懈倒序收尾，最后完成原牌；每张均有明确被反制对象 |
| 伤害 | 本批普通杀与决斗造成1点伤害，记录来源、目标、原始使用实体牌与数值；体力降至0或以下挂起救援 |
| 救援顺序 | 从当前回合单位开始，沿存活座次环依次询问，包含濒死者；每位救援者可连续用桃或放弃；回复到正体力才结束救援 |
| 救援失败 | 所有存活单位放弃后，濒死者死亡、手牌进弃牌堆；没有身份奖惩；死亡位置退出距离图与后续回合 |
| 牌堆不足 | 仅将弃牌堆重新洗入摸牌堆；处理区始终排除；仍不足时记录`draw.exhausted`并停止本次剩余摸牌，不产生胜利 |
| 终局 | 当前效果栈清空后，一方无存活单位则另一方胜；无车轮替补、战役胜利ID或占城事件 |

上表是当前可执行的开发合同。开局发牌顺序、先手摸牌、距离、救援顺序、无懈询问顺序、洗牌及无牌处理仍须对照同一OL PC快照核验；如有差异须改实现或登记项目裁定，不能将本表当作冻结的OL裁定。负体力连续救援已有注入稳定状态的回归，但本批伤害只为1点，不宣称多点伤害或技能已接入。

## 3 结算与决策契约

使用杀时实体牌进入处理区，压入`FinishCard`帧和`Dodge`帧。目标放弃闪后，以显式`Damage`帧结算伤害；需要时压入`Rescue`帧并记录救援游标。伤害不需要选择时自动推进，稳定暂停点保留等待闪、决斗出杀、无懈或桃救援的帧及其收尾帧。救援和死亡清理完成后才执行原使用牌的`FinishCard`，再判断终局。闪、决斗响应杀与桃自身的支付立即完成，原使用牌在其响应全程留在处理区。

决斗或无中生有先压入原牌`FinishCard`、`Duel`或`DrawCards`效果帧、`Nullification`窗口。每张无懈新增一个带`CounteredCardId`的收尾帧，并更新窗口的当前牌、来源、`ChainDepth`和连续放弃游标；窗口关闭后用链的奇偶决定保留或移除原效果。随后倒序完成各无懈的收尾，执行仍有效的原效果，最后完成原牌。这是当前无技能单目标锦囊的显式链模型，尚未实现任意武将触发或多目标嵌套。

决斗`Duel`帧的来源与目标在每次成功响应后交换，游标记录响应轮数；当前目标是应出杀者，放弃时由当前来源造成伤害，归因实体始终为原决斗。若发起者濒死则可在原回合自救，救活继续出牌；死亡则先完成结算，再进入下一个存活单位。无懈牌在链关闭后先入弃牌堆，因此原无中生有后续摸牌时可以洗回已收尾的无懈；原无中生有自身仍处于处理区。

每个稳定状态携带唯一实体牌清单，实际摸牌堆、各单位手牌、处理区和弃牌堆的并集必须恰好等于清单，不能重复、缺失或增加实例。快照还校验体力/存活状态、双方容量、连续座次、帧来源与目标、支付牌、游标、待决策请求及命令记录。日志按连续序号记录抽牌、杀、响应、伤害、回复、濒死、死亡和终局。

命令包含`CommandId`、预期版本、控制者、请求ID、操作单位及动作。应用层先检查重复ID，再检查版本和权限，最后以规则核心提供的合法动作检验时机、支付、目标、范围和次数。无懈动作额外携带`ResponseToCardId`，必须等于窗口中最新待反制牌；决斗响应使用独立`RespondSlash`动作。完全相同的重复命令返回原提交结果；同ID不同输入拒绝。被拒绝的命令不提交状态、不消耗随机流、不增加日志或扣牌。救援中连续用桃、无懈后重新询问也会更新版本和请求ID。

`BattleView`公开体力、队伍、座次、手牌数、处理区和弃牌堆；只给控制者自己的手牌。新增`BattleResponse`公开当前效果类型、来源、目标、关联牌和反制层数，供界面和脚本解释操作对象。摸牌堆只给数量，不提供顺序和随机状态；只有当前控制者能取得合法动作及其支付牌。完整`BattleState`及内部事件日志只供规则、存档和开发工具使用，不能直接绑定客户端或AI。当前演示脚本只读取操作控制者的视图，它是固定操作脚本，尚未实现正式战术AI。

## 4 开发快照及复现

基础战斗快照使用格式ID`sanguo.basic-battle`、格式版本2，记录引擎`0.3.0-basic-development`、规则包v2、场景内容摘要、随机流、全部区域、效果帧、请求、日志和去重记录。信封采用SHA-256检测损坏，恢复时检查版本、预期内容摘要和领域语义；不兼容快照直接拒绝。旧格式1、旧引擎0.2及旧规则v1均返回`save.incompatible`，本批不提供活动开发牌局迁移；G0抽牌存档格式不变。

本批只实现编解码。命令行输出的是开发证据文件，尚未接入G0的原子替换、备份回退文件服务或Godot保存按钮；不应将其作为玩家存档服务的已完成验收。

```sh
# 全量回归，含独立进程恢复后final.json逐字节比对
./scripts/check.sh

# 合成64张牌、通用单位2对2、种子42
./scripts/dotnet.sh run --project tools/Sanguo.Simulator -- --battle-basic 42 build/basic-battle

# 新进程读取最后一个稳定决策点并继续
./scripts/dotnet.sh run --project tools/Sanguo.Simulator -- --battle-resume build/basic-battle/checkpoint.json build/basic-battle/resumed
cmp build/basic-battle/final.json build/basic-battle/resumed/final.json

# 六种牌的合成场景；包含真实反无懈链和决斗
./scripts/dotnet.sh run --project tools/Sanguo.Simulator -- --battle-tricks 42 build/trick-battle

# 两个新进程分别从二层反制中间、首个决斗响应点继续
./scripts/dotnet.sh run --project tools/Sanguo.Simulator -- --battle-tricks-resume build/trick-battle/counter-chain.json build/trick-battle/resumed-counter
cmp build/trick-battle/final.json build/trick-battle/resumed-counter/final.json
./scripts/dotnet.sh run --project tools/Sanguo.Simulator -- --battle-tricks-resume build/trick-battle/duel-response.json build/trick-battle/resumed-duel
cmp build/trick-battle/final.json build/trick-battle/resumed-duel/final.json
```

输出`checkpoint.json`、`final.json`、内部`events.json`和`report.json`；遇到二层及以上反制、决斗响应时还分别保留第一份`counter-chain.json`、`duel-response.json`。逐决策执行“写文件→读文件→提交同一命令→比较哈希→重提命令确认幂等”。报告按出牌、弃牌、闪响应、无懈窗口、决斗响应和救援记录恢复数量；超过4000步视为失败，不产生胜利。证据目录必须使用独立目录，脚本会覆盖同名开发证据文件。三牌与六牌场景的内容摘要不同，恢复时须使用对应入口。

v2下种子42三牌场景实际完成26个角色回合、105条命令；恢复点分别为出牌55、弃牌17、闪响应26、救援7。终态SHA-256：`0c78d41b62265ef77aa0b20e3753ced14fb39389e4c5a6db0cbe482041020857`。独立进程从最后救援点恢复后，终态快照与连续执行逐字节一致。该哈希随本次引擎、规则和状态字段升级变化，原v1哈希只适用于历史构建。

种子42六牌场景实际完成15个角色回合、118条命令；恢复点分别为出牌33、弃牌7、闪响应9、无懈窗口44、决斗响应18、救援7，最大反制深度3。从反制链、决斗快照分别启动新进程后还执行92、104条命令，最终文件均与连续版逐字节一致。终态SHA-256：`3bf6ab7dd19bc8f7e898066421206c5e5424ddac61153db297216d6df8581a21`。

## 5 验证范围与后续

首批33项xUnit检查包含杀闪牌去向、伤害来源、桃使用资格、主动杀次数、距离、弃牌、负体力救援、自救、救援座次环绕、全员放弃后的死亡清理、死亡后距离和回合、空牌堆、洗牌随机恢复、非法命令不变、共享控制者的实体权限、并发/重载幂等、可见信息隔离及快照篡改和语义错误。

首批批量检查覆盖16种双方人数配置和100个固定种子的2对2合成杀牌对局。锦囊批次新增36项检查，覆盖0至4层反制及对象绑定、决斗交替与主动杀次数、双向伤害和发起者死亡/自救、无中生有牌堆不足与处理区排除、已完成反制牌洗回、公开响应视图、非法链和旧版本拒绝；其中新增100种子的六牌混合对局覆盖全部16种人数配置，实际执行了交替出杀与二层以上反无懈。全部批量样本逐决策编码恢复、执行同一命令并比较完整哈希，持续校验牌守恒及重复命令幂等。

完整`check.sh`当前通过160项xUnit及13项Python检查，G0原终态哈希不变。这些样本不含正式OL武将、拆顺与完整客户端，不充作M1全部内容的100场验收。

下一步补齐拆顺目标区域和暗牌选择、扩展武将触发框架，再接入关羽、曹操与奋击；客户端消费控制者视图和合法动作。正式规则及UI还原仍需来源冻结和对应验收证据。
