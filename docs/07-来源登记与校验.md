# 三国行纪 来源登记与校验

三份来源清单现由`Sanguo.ContentValidator`统一检查：规则`rules-reference.json`、武将`sgsol-generals.json`、界面`sgsol-battle-ui-reference.json`，均位于`content/manifests/`。校验器不联网、不更改清单状态，也不把采集待办补成已核验数据。

## 运行方式

```sh
# 普通开发检查：试验牌有效、清单结构和已登记证据有效即可通过；同时列出来源待办
./scripts/dotnet.sh run --project tools/Sanguo.ContentValidator -- content

# 来源冻结严格检查：在普通检查基础上，所有清单及子条目必须冻结，适配映射必须完成
./scripts/dotnet.sh run --project tools/Sanguo.ContentValidator -- content --require-frozen
```

返回值：`0`为对应模式通过，`1`为校验失败，`2`为参数错误。`./scripts/check.sh`调用普通模式，避免真实采集前阻断纯工程检查；严格模式需在来源收口时单独执行。当前仓库仍为草稿，严格检查返回`1`是预期结果，不能计为冻结通过或G0通过。

错误和待办均输出`文件:JSON字段 [错误码] 说明`。结构错误、缺失文件或不匹配证据在普通模式也会失败。所有对象拒绝未知字段和重复JSON属性；必需字段不能遗漏。待采集元数据保留`null`，集合保留空数组。

## 状态与冻结要求

所有清单固定`formatVersion=1`、`sourceGame=sgs_online`，根对象均登记`sourceSnapshotId`和`clientVersion`。任何已填入的根快照或客户端版本在三份清单间必须一致；证据与其所在清单也必须一致。

| 清单 | 草稿状态 | 标记`frozen`后的必需内容 |
| --- | --- | --- |
| 规则 | `pending_verification` | 非空快照、客户端版本、有效`frozenAt`日期；非空`deckList`和`rulings`字符串索引；`rules`及`ruling`证据；`blockingItems`清空 |
| 武将 | 根及人物均为`pending_verification` | 根元数据完整，全部人物冻结；每人具备`variantId`、`portraitId`、基础属性、完整技能登记、规则案例索引及`general`和`portrait`证据 |
| 界面 | 根及交互状态均为`pending_capture` | 根元数据、主题、正数分辨率与缩放、有效`capturedAt`日期；截图和录像索引、全部交互状态冻结、适配映射完成 |

人物目录必须保留MVP六人登记，人物ID、每人技能ID和规则案例索引不得重复。`baseAttributes`使用`maxHp`（正整数）、`gender`、`faction`；`completeSkills`为`{ "skillId": "来源技能ID", "text": "完整来源技能文本" }`对象数组。`skinId`可为空，表示使用登记原画。未冻结人物的`includedInRuntime`必须为`false`；冻结本身不证明该人物技能已实现，运行包能力和规则案例仍需后续验收。

界面必须保留空闲、出牌、选牌目标、杀闪、决斗、无懈、技能、目标区域选牌、弃牌和濒死十类状态，状态ID不得重复。`screenshots`与`recordings`是当前界面清单`evidence`内的证据ID数组，必须匹配证据类型。每个已冻结交互状态的`evidence`同样引用证据ID，且须同时包含截图和录像。`adaptations`的ID不得重复，状态只接受`specified`（映射说明已确定）或`awaiting_reference_mapping`（待映射）；存在后者时不能冻结。

## 本地证据格式

规则清单和每名武将的`evidence`、界面清单的`evidence`均使用以下对象数组。示例仅说明格式，实际登记必须替换为真实来源文件及摘要：

```json
{
  "id": "证据唯一ID",
  "kind": "screenshot",
  "path": "evidence/实际截图.png",
  "sha256": "实际文件的64位十六进制SHA-256摘要",
  "sourceUrl": "https://实际来源地址",
  "sourceSnapshotId": "与所在清单一致的快照ID",
  "clientVersion": "与所在清单一致的客户端版本"
}
```

`kind`支持`rules`、`ruling`、`general`、`portrait`、`screenshot`、`recording`。证据ID在所在证据数组内唯一；不同人物的数组独立。`path`相对于`content/`，禁止绝对路径、上级跳转及符号链接。校验器读取实际文件计算SHA-256，与登记摘要逐字比对（十六进制大小写均可）；缺失、不可读、摘要无效或不匹配均失败。证据在草稿阶段一旦登记，也执行同样检查。

## 校验边界

通过严格模式仅表示登记结构、状态、引用和本地文件摘要符合约定。程序不会判断截图是否真的来自指定OL客户端、媒体是否覆盖所声明的操作、皮肤是否属于所选版本、技能文本是否完整正确，也不会检查规则案例ID是否已有可运行实现或资产是否适用于公开分发。这些仍须按战斗附录和界面规范人工核验，不能凭`frozen`字段或程序返回码关闭M0、M1及U系列验收。

测试中的冻结样本是临时目录内的合成文本，使用`example.invalid`地址；仅验证拒绝与通过路径，绝不作为OL采集证据或运行内容。来源证据不参与当前`g0-probe`牌内容哈希，现有试验存档及种子42的终态哈希保持一致；正式规则包及其存档绑定仍待实现。
